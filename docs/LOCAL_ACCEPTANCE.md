## One acceptance command

~~~bash
make verify-local
~~~

This executes 19 serial steps: Python/frontend/source-engine/browser-driver checks, Compose parsing, isolated standards, real core/routes/Group, selected HTTP/hazards/faults/CSE recovery/observer measurements, then actual rendered HTTP/HTTPS browser and certificate/role checks. It writes a per-step log, exit code, PASS/FAIL, unattempted count and final summary under a new ignored evidence directory. A failed step stops the plan. BLOCKED means an unmet prerequisite, not product success. Inspect the failing step log and its child evidence rather than repeating unrelated tests.

The main acceptance services use a unique Compose project and four distinct loopback ports allocated by the OS with port 0. The selected CSE/legacy/selected-HTTP/HTTPS ports are recorded in the run's meta.json and passed consistently to Compose, browser commands and HTTPS checks. They no longer assume that 18080/13000/13001/13443 are free. Selections are held together during allocation, then released before Compose binds; an unrelated process may still win a later race, which remains an explicit startup failure. No existing listener is killed. The standards stack has its own project suffix/volumes/network and no host ports. Cleanup stops only the test projects and retains volumes/evidence. The normal demo keeps its existing ports and is not intentionally reset. Continue running one acceptance plan at a time.

T32 standards requires real CSE label discovery and read-back for all eight registered AEs plus an actual empty negative query. A sensor CREATE/RETRIEVE over TS-0010 MQTT must match HTTP CIN read-back and a durable actual HTTP SUB event; forbidden sensor route writes and resident telemetry reads must be denied. MQTT PUBACK alone cannot pass. No arbitrary JSON/broker message or mocked CSE supplies success. This isolated broker is anonymous/plaintext, unexposed on the host; it is not full MQTT authentication/TLS or SDT/SAREF Expert evidence.

T33 browser uses a temporary Chrome profile and pipe, separate resident/responder cookie contexts, actual controls/DOM/SVG and real same-origin APIs. It resets to a new incident, checks both modes/170 residents, selection across polling, advancement/conservation/ACK rendering, playback/pause, role denial, a 390-pixel viewport, 31-second expiry/history and logout. Screenshots and assertions are private evidence. Correlate its incident/version with the actual application's CSE/Group/device artifacts; a browser-only result does not independently prove CSE authenticity. Failed startup is BLOCKED, not a renderer PASS. It preserves Chrome sandbox and captures no passwords/cookies/network login bodies.

For a browser-stage failure after backend gates pass, run make p1-browser to rebuild/start the normal selected HTTP demo and retest that flow directly; this creates a fresh incident. Backend READY and rendered button readiness are different: the driver waits for a visible, enabled, unobstructed control before dispatching exactly one mouse press/release pair. It never replays a possibly dispatched action automatically. Failures retain a fixed error code, boolean control/DOM state and, only after login is hidden and its password field cleared, a private failure screenshot. Raw exceptions/evaluated login code/response bodies are not exported. The previously lossy reason=Error is not proof that a test assertion passed.

If the normal HTTP demo is already healthy at port 3001 and only tests/browser files changed, use make test-browser to rerun without rebuilding containers. It still logs in and resets to a fresh incident. Keep it serial with all other scenario/demo tests. Use make p1-browser when the app is stopped or its image needs rebuilding; an HTTPS-only demo requires its matching --https browser command above.

Each new role context must reach the exact destination URL with document.readyState=complete before the driver touches the form. An existing parser-created form alone is insufficient: deferred module scripts may not have registered listeners. The read-only document predicate has a 30-second budget plus any in-flight CDP deadline; DOCUMENT_NOT_READY is a failure, not a successful skip. The single login submission has a temporary listener registered after the app handler; if the app has not prevented default, the guard prevents native GET navigation, clears the password, and reports LOGIN_HANDLER_NOT_READY without replaying a possibly sent POST. Separate RESIDENT_NAVIGATION/RESIDENT_LOGIN/RESIDENT_ISOLATION phases and active-page boolean diagnostics identify the affected role. Screenshots remain disabled while its password is present or login is visible. meta.json hashes the dashboard and its three helper modules; no credential or evaluated login expression is stored.

T34 HTTPS wraps the actual selected API in a TLS>=1.2 context, with Secure/HttpOnly/SameSite session cookies. Files under .runtime/tls are generated once and validated on reuse; incomplete files are never silently overwritten. Only server certificate/key and public CA are mounted, never the CA private key. make test-https verifies the local CA and hostname, actual negotiated version, anonymous 401, authenticated role sessions and rejection of an untrusted CA. The browser test pins only the generated development certificate's public key in its temporary test profile. It does not disable all certificate checking. A normal browser must trust this local CA separately; no system trust store is changed automatically.

HTTPS protects browser-to-API transport only. CSE originator headers and the isolated MQTT broker are not cryptographically bound to actor identities by this increment. Keep the deployment local/private and state that full CSE authentication/TLS is unfinished. The normal make demo-scenario-up command returns to the existing HTTP development profile.
